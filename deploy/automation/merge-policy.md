# Upstream merge policy

You are resolving an in-progress `git merge --no-ff --no-commit` of an upstream
Twenty release tag into our fork, or fixing a verification failure (typecheck,
build, install) left by that merge. The working tree is the merge state.

## Rules

- Upstream's structure wins. Re-apply our change on top of upstream's new code.
  Never keep a stale copy of a file upstream rewrote.
- If upstream deleted a file we modified, accept the deletion. Port our change to
  where the code moved only if it still applies; otherwise drop it and list it in
  the summary.
- If upstream already fixed what a fork commit fixed, take upstream's version.
- Conflicts only: touch only conflicted files and what the verification error
  requires. No new features, no refactors, no dependency changes beyond what the
  merge brings.
- Never rewrite or delete committed instance/upgrade command `up`/`down` logic.

## Fork behaviour that must survive

- Env-driven branding: `APP_NAME`, `APP_LOGO_URL`, `APP_EMAIL_LOGO_URL`,
  `APP_WEBSITE_URL`, `APP_SOURCE_URL` in `config-variables.ts`;
  `appName`/`appLogoUrl`/`isLandingPageEnabled` in client-config; front states
  `appNameState`/`appLogoUrlState`/`isLandingPageEnabledState`; auth `Logo`,
  `FooterNote`, `PageTitle` suffix, neutral `index.html` title;
  `packages/twenty-emails` `utils/branding.ts` and its consumers. With
  `APP_NAME=Twenty` behaviour must equal upstream.
- `MAX_WORKSPACES_LIMIT` in sign-in-up and workspace creation.
- The landing page (`pages/landing/*`, `IndexPageRouter`).
- `deploy/**`, `integrations/**`, `docs/SAAS_DEPLOYMENT.md`.
- The `run-skipped-instance-commands` CLI command
  (`packages/twenty-server/src/database/commands/run-skipped-instance-commands.command.ts`,
  its selection util `select-skipped-instance-steps.util.ts`, the
  `RunSkippedInstanceCommandsCommand` registration in
  `database-command.module.ts`, and `resolveStartCursor` staying public in
  `upgrade-sequence-runner.service.ts`). `deploy/oracle/deploy.sh` calls it
  before `upgrade`.
- Our `.github/workflows/`. Never restore upstream workflows; they are removed on
  purpose.
- Our Dockerfile delta: no `VOLUME` line.

## `.po` files

Take upstream's entries and structure. Keep our Spanish `msgstr` where the msgid
still exists: `People` -> "Contactos", `Person` -> "Contacto",
`Point of Contact` -> "Persona de contacto". Compiled catalogs under
`locales/generated/` are regenerated by the verify step: take upstream's copy.

## Process

1. List conflicts with `git diff --name-only --diff-filter=U`. Resolve each,
   remove every conflict marker, and `git add` the file.
2. If verification failed, read the error output given to you, fix the cause with
   the smallest change, and re-run only the failing command to check.
3. Do not commit, push, create branches, or touch git history or config. The
   workflow script owns the commit. Do not add any attribution text anywhere.
4. Finish by appending a short summary to `$GITHUB_STEP_SUMMARY`: what conflicted,
   how each was resolved, and what was dropped.
